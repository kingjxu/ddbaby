# 2026-10-10 Hero 首次结果全链路时延审计

## 结论

本次冻结 `2026-10-10 13:58:00` 至 `14:16:07 +08:00` 的生产日志和 60 张 `*-hero.jpg`，按 1.0.27 的 `decision_cycle_id` 统计同一 Hero 决策机会的首次实际展示。重复 Hero 结果、decided 帧和其他玩家行动时间均未计入主指标。

- 19 个产生首次展示的决策机会中，`hero_turn_detected -> first_display` 平均 **2.828s**、P50 **2.788s**、P95 **3.490s**、最大 **4.448s**；6/19 超过 3 秒，1/19 超过 4 秒。用户感知到 3 秒以上与真实 trace 一致。
- 最大耗时在服务端识别：平均 **1.914s**，约占首次展示总耗时的 **67.7%**；P95 **2.573s**、最大 **2.647s**。识别耗时与总耗时的样本相关系数为 0.668，是当前首要瓶颈。
- 公网传输及 HTTP 客户端/代理开销（扣除服务端总耗时）平均 **484ms**、P95 **795ms**，约占总耗时的 **17.1%**，是第二大耗时来源。请求体实际写入平均仅 7ms，主要不是 JPEG 上传写入本身。
- 客户端从首次检测到 Hero 到采集图片平均 **208ms**、P95 **687ms**、最大 **781ms**；从检测到发起 HTTP 平均 **340ms**、P95 **820ms**、最大 **913ms**。这批样本不支持“普遍轮到 Hero 后约 1 秒才截图”的判断，但局部样本确有接近 1 秒的前置长尾。
- 决策服务平均 **74ms**、P50 **43ms**、P95 **180ms**；仅一条为 502ms。响应返回到悬浮窗首次展示平均 **15ms**。两者均不是整体 3 秒体感的主要来源。
- 完整性比成功样本的时延更值得优先处理：35 个客户端 Hero cycle 中，19 个有首次展示，另 16 个没有首次展示记录。其中 11 个深色桌面 cycle 的识别结果在 GTO 前因请求非法被拒绝，3 个真实牌桌 cycle 识别不完整，另有 2 个手机桌面误触发。该 16 个 cycle 不应混入时延分位数，但代表“没有结果”的独立问题。
- 若把“准确”定义为真实牌桌上形成可用决策状态，本窗口为 **19/33 cycle（57.6%）**；按请求为 **40/72（55.6%）**。40 次进入决策的结果经原图明显错误筛查，Hero 手牌、公共牌、Hero stack、主池、盲注和 BTN 未发现明显不一致，但这只是已成功样本的条件准确性，不代表端到端识别率。

因此建议先优化服务端识别路径，同时修复深色桌面 ROI、Hero 位 BTN 边界和客户端牌桌存在性门控；随后再降低约 0.5 秒的公网往返长尾。客户端采集调度可以作为第三优先级优化，但不是本批 3 秒体感的主因。

## 线上识别准确性

识别准确性必须分两层看：成功进入决策的结果是否有明显识别错误，以及真实牌桌请求能否形成可用决策状态。只统计前者会隐藏大量没有结果的请求。

| 口径 | 成功/总数 | 比例 | 说明 |
| --- | ---: | ---: | --- |
| 决策机会级，全部客户端 Hero cycle | 19/35 | 54.3% | 包含 2 个手机桌面误触发 cycle |
| 决策机会级，仅真实牌桌 | 19/33 | 57.6% | 11 个深色布局失败，3 个真实牌桌识别不完整 |
| 请求级，仅真实牌桌 | 40/72 | 55.6% | 同一 cycle 的重复帧不独立，因此以 cycle 口径为主 |
| 已进入决策请求的核心字段筛查 | 40/40 | 100% 未见明显错误 | 条件准确性；不包含未形成完整状态的请求 |

40 次有效决策请求对应的现场图中，Hero 手牌、公共牌、Hero stack、主池、盲注和 BTN 与日志未发现明显不一致。该结果仅说明“系统已经接受的样本”质量尚可；没有逐像素标注所有对手 stack、bet 和 status，不能表述为全部字段 100% 准确。

失败集中在三类确定性问题：

1. **深色桌面布局未适配**：11 个 cycle、20 次请求。原图可见不同 Hero 手牌和非零 stack，生产却反复识别为单张 `4♠/4♥`，其中 17 次 Hero stack=0，3 次只有一张手牌，全部在调用 GTO 前被拒绝。这是布局/ROI 系统性偏移，不是决策算法问题。
2. **Hero 位 BTN 漏检**：2 个 cycle、11 次请求。两组绿桌图片的手牌、stack、底池和盲注均完整，但 `button_seat=null`。原图可见 Hero 旁白色 `D`；现场轮廓 circularity 为 0.399，通用阈值要求至少 0.40，Hero fallback 又要求更大面积，因此稳定漏过边界。
3. **误触发与单帧异常**：2 个手机桌面 cycle 被客户端固定 ROI 的红绿颜色门控误判为 Hero；另有 1 个真实牌桌请求耗时 6.419s 后返回伪造般的 flop/四张牌/stack0 结果。该单帧异常与原图明显不符，但仅凭现有日志不能进一步确认是并发污染、模型异常还是识别服务内部状态问题。

本次复核还修正了初版日志关联：服务端允许多请求并发，不能用一个全局“当前 trace”绑定识别响应。现按每个 trace 的 stage 到 terminal 区间，并用 `server_recognize_ms` 匹配未分配响应；2,040 个 stage、2,040 个 terminal timing 和 2,040 个识别响应全部一一关联，未分配和冲突均为 0。首次展示的 19 条时延由客户端完成头直接携带，不受该修正影响。

## 没有首次结果的 cycle

35 个 cycle 的最终分类：

| 分类 | cycle 数 | 含义 |
| --- | ---: | --- |
| 首次展示完成 | 19 | 有合法决策且客户端回传首次展示 |
| 非法决策请求 | 11 | 识别完成，但请求在调用 GTO 前被校验器拒绝 |
| 识别不完整 | 5 | 3 个真实牌桌 cycle、2 个手机桌面误触发 cycle，服务端均未形成完整扑克状态 |

11 个非法请求 cycle 共包含 20 次 Hero 请求：17 次为当前 Hero `stack=0`，3 次只有一张 Hero 手牌。非法识别请求的识别耗时平均 3.906s、P95 4.973s、最大 5.325s；14 次识别不完整请求平均 2.558s、P95 5.898s、最大 6.419s。相比之下，40 次进入有效决策的 Hero 识别平均 1.903s、P95 2.567s、最大 2.780s。

这说明异常识别同时造成两种影响：一是识别耗时更长，二是最终没有可展示结果。它们不能作为已完成请求的普通长尾处理。比如 `13:58:32-hero.jpg` 原图可见 K♥4♦ 和 Hero stack 876，生产识别只得到一张 `4♥` 且 stack 0，随后在 GTO 前被拒绝；这是明确的识别问题，不是决策服务慢。

## 优化顺序与验收口径

1. **服务端识别**：为 Hero 全量识别补充内部阶段计时，定位 rank/suit、玩家 OCR、公共信息 OCR 中的主要耗时；对同一 cycle 的稳定桌面区域复用结果，避免重复完成全桌 OCR。验收看 `server_recognize_ms`，目标先将 P50 从 1.858s 降到 1.2s 以下、P95 从 2.573s 降到 1.8s 以下。
2. **识别完整性**：先适配深色桌面 Hero 手牌/stack ROI，再放宽并重测 Hero 位 BTN 的轮廓边界，同时给客户端 Hero 检测增加牌桌存在性门控。不能用默认 stack、补牌或猜 BTN 兜底进入决策；修复后以同一批原图重放，要求完整状态才调用 GTO。
3. **网络链路**：拆分 DNS/建连/TLS/首字节/下载，确认平均约 0.48s 的服务端外耗时在哪一段；优先验证连接复用。验收看 `transport_excluding_body_write_ms` 的 P95。
4. **客户端前置时间**：保留 `hero_turn_detected -> capture -> HTTP start` 指标，排查最慢 0.8～0.9s 的采集调度；不得把被覆盖旧帧的 `queue_backlog` 重复计入用户等待。
5. **最终验收**：继续只按 `decision_cycle_id` 的首次 `client_complete` 统计，同时报告“有首次结果的 cycle 比例”。只降低成功请求的 P95、但仍有 cycle 无结果，不能视为体验问题已解决。
